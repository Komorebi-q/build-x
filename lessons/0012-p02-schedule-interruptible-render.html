P02 · Scheduling

在节点边界暂停，而不是猜一个延时

把 Fiber 遍历放进可控工作循环：每完成一个工作单元就检查预算，必要时保存 next 指针并把控制权交还宿主。

50–75 分钟难度：中等产出：确定性分片测试

先分清“安排一轮”与“执行一轮”

schedule callback
→
处理若干 units
→
shouldYield?
→
保存 next / 再安排

调度器不需要理解 Fiber。它只提供“稍后再运行”和“本轮是否该让出”的信号；renderer 决定每个 unit 是什么，并持有剩余工作。

教学近似

原始 Didact 教程使用 requestIdleCallback 展示空闲切片。它不是跨环境的稳定基础，也不等于现代 React Scheduler。为便于测试，先设计可注入的调度边界。

用契约定义 scheduler，而不是绑定某个 API

schedule(workLoop)
  约定：不会立刻递归调用 workLoop

workLoop(budget)
  while 仍有 nextUnit 且 budget 允许：
    nextUnit = performUnit(nextUnit)
  若仍有工作：安排下一轮
  若候选树完成：交给 commit 阶段

这段是控制流伪代码，不是实现答案。你需要自己选择 scheduler 适配器，并让测试不依赖真实时间。

1

做一个手动预算测试替身

测试可以指定“一轮最多允许处理 N 个 unit”，并显式运行下一轮。它至少要暴露：已安排回调数量、每轮访问节点、剩余 nextUnit。

交付：无需 sleep 的 scheduler 契约测试。

四个必须证明的分片场景

场景第一轮后最终
预算足够nextUnit 为空，候选树完整只需一轮
预算为一个 unit恰处理一个节点，nextUnit 指向后继多轮访问序列仍正确
深层回溯处让出恢复点不丢失叔叔节点仍会被处理
空队列再次调度不产生无意义工作不会重复 commit
2

比较单轮与多轮访问轨迹

同一棵树分别用无限预算、每轮一个 unit、交替预算运行。最终访问序列和生成的候选树应等价。

交付：三种预算下的差分测试和一张轮次记录表。

证明“让出”真的有意义

构造一个足够大的纯 element 树，并安排一个独立的高优先级观察任务。比较整树同步递归与分片版本：不要只比较总耗时，还要记录观察任务最迟多久获得执行机会。

本实验关注响应性，不预设分片版本总耗时更短。切片和重新调度本身有成本。

3

记录吞吐与响应性的取舍

至少记录总完成时间、轮次数、单轮最大工作量、观察任务等待时间。说明你的实验噪声来源。

交付：一张测量表和三句结论，不以单次结果下定论。

逐级提示

提示 1：工作为什么重复了

检查 nextUnit 是在处理前还是处理后更新，以及让出时是否保留了唯一的恢复点。

提示 2：测试偶尔失败

把真实时间、浏览器空闲度和 timer 从单元测试移走；单元测试只控制预算和回调队列。

提示 3：循环永不结束

分别断言“performUnit 必须推进 next”与“无 next 时不得继续 schedule”。不要只在整合测试里找原因。
