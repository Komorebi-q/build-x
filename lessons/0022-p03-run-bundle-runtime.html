用局部 require 走完模块图

现在让产物真正执行。重点不是函数有多短，而是每次加载都使用当前父模块的 mapping，把源码 specifier 翻译成 child id，并维持模块作用域与导出对象。

50–75 分钟核心：加载契约产出：执行轨迹与 runtime 测试

先理解两级查找

parent code
→
localRequire(specifier)
→
parent mapping
→
require(childId)

require(id) 能查全局模块表；转换后的业务代码却只保留原始字符串，例如 require("./util.js")。因此 runtime 必须为每个父模块创建一个闭包，让它携带该父模块自己的 mapping。

不能建立一张全局 specifier → id 表

features/a.js 和 features/b.js 都可能导入 ./util.js，但目标不同。specifier 只有结合 importer 才有解析意义；build-time mapping 把这个语境带进 runtime。

画完整执行轨迹

先依据转换后的代码预测，再运行产物采集日志。不要只写最终 hello world；要显示进入 wrapper、解析局部 specifier、返回 exports 和退出 wrapper。

交付：完整轨迹表和一张调用栈图。

runtime 的最小数据契约

加载模块(moduleId):
  从 module table 取 wrapper 与当前模块 mapping
  创建本次模块实例，初始 exports 是一个对象
  创建只读当前 mapping 的 localRequire
  调用 wrapper(localRequire, module, module.exports)
  返回 module.exports

localRequire(rawSpecifier):
  在当前模块 mapping 中找到 childId
  调用“加载模块(childId)”

这是伪代码。你需要亲自决定并测试错误处理、入口返回值和调试日志接口。核心阶段暂不加入缓存，以便在菱形依赖中清楚观察“图节点去重但执行未去重”的差异。

对象初始关系常见误解
module持有可替换的 module.exports它不是所有模块共享的全局对象
exports 形参开始时指向同一个初始导出对象给局部 exports 重新赋值不等于替换 module.exports
localRequire闭包捕获当前模块 mapping它不是 Node 完整的 require

亲自完成：让入口启动并保留可观察性

2

以失败优先实现 runtime

  1. 单模块：入口业务日志准确执行一次。
  2. 嵌套链：依赖先完成导出，父模块再继续使用返回值。
  3. 父级语境：两个目录各自的 ./util.js 必须加载到不同 child id。
  4. 默认与命名导出：结果符合你选定 Babel transform 的输出契约。
  5. 缺 mapping：错误指出 parent id 与 raw specifier。
  6. 缺模块记录：错误指出 child id，不能只出现难懂的解构异常。

交付：六组 runtime 测试与一条真实嵌套执行日志。

让测试捕获日志，而不是污染断言

测试运行生成程序时，建议把业务侧 console 或 runtime trace 注入/截获到列表，再对事件序列断言。至少区分：

  • build trace：读文件、解析、发现边、分配 id；
  • runtime trace：进入模块、解析局部请求、返回导出、退出模块；
  • application output：待打包程序自己的日志或结果。

三类日志混在一起时，“构建阶段意外执行源码”很容易被忽略。

提示 1：嵌套执行顺序

父 wrapper 调用 localRequire 时会暂停，直到 child wrapper 返回 exports。业务日志顺序应由转换代码里的 require 位置决定。

提示 2：错误早一点

localRequire 在调用 child loader 前先验证 raw specifier 是否存在于当前 mapping，能生成更接近源代码的错误。

提示 3：为何现在不加缓存

先用菱形夹具看清无缓存行为，再添加缓存，才能说明它改变了哪个不变量，而不是把一段 Map 代码当魔法。
