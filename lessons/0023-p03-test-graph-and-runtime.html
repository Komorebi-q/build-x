别让一个 hello world 替整个流水线作证

最终输出正确可能只是巧合。本课把 parser、resolver、graph、serializer 与 runtime 分层验证，再用链式和菱形夹具证明它们连接正确。

55–80 分钟核心：测试分层产出：P03 测试证据包

建立证据矩阵

层级最低证据它排除的假阳性
asset 单元测试AST 依赖列表、转换结果关键形状、语法错误位置正则恰好匹配简单示例
resolver 单元测试importer + specifier → canonical filename只在当前工作目录碰巧可用
graph 单元测试节点身份、边、局部 mapping、菱形去重最终日志正确但图重复或边接错
serializer 契约测试产物可解析、作用域隔离、输出确定runtime 还没走到损坏文本
runtime 单元测试局部请求、exports、错误语境、执行轨迹只在一层依赖时看不出 mapping 错位
端到端测试真实夹具 → bundle → 隔离执行 → 业务结果各函数单独正确但契约连接失败

四个核心夹具，各自只证明一件难事

A · 单模块

证明入口、wrapper、业务日志和无依赖 mapping 的最小闭环。

B · 三层链

证明递归发现、每层相对解析、依赖先返回再恢复父模块。

C · 同名局部依赖

两个目录都写 ./util.js，证明 mapping 属于 importer。

D · 菱形共享依赖

证明图节点去重，并显式观察有无 runtime cache 的执行差异。

1

为每个夹具写“只看最终值不够”的断言

每个夹具至少包含一个结构断言和一个行为断言。例如菱形既断言 shared 在图中只有一个 id，也用副作用计数记录 shared wrapper 实际执行几次。

交付：夹具拓扑图、预期节点/边表、行为事件序列。

菱形依赖：把三个结论分别写出来

观察核心期预期如何解释
shared 源文件被分析几次一次canonical filename 索引避免重复 asset
有几条边指向 shared id两条共享节点仍保留两个父关系
shared wrapper 执行几次取决于已声明缓存策略核心若不含缓存，应明确记录两次及其与 ESM 的差距

若你提前实现了缓存，测试应期待一次；若按课程核心暂不缓存，测试应把“两次”命名为已知教学限制，而不是把它当理想语义。第 7 课再用状态表加入缓存。

负向测试：错误也要跨阶段保留语境

2

至少完成四条失败路径

  1. 非法语法：文件名、行、列和 parser 原因可见。
  2. 不支持的 specifier：明确规则与收到的值，不尝试猜包名。
  3. 文件不存在：包含 importer、raw specifier 与候选 canonical path。
  4. runtime mapping 缺失：包含 parent module id 与请求字符串。

交付：错误快照或结构化字段断言。不要只断言“会 throw”。

构建失败时不要留下貌似成功的旧产物

若你的 CLI 写文件，先在内存完成建图和生成，再以明确策略更新输出。至少用测试证明失败不会把半截 bundle 当作最新成功结果。

确定性与可观察图

固定输入连续构建两次，比较：

  • 节点列表与边列表；
  • 模块 id 分配；
  • 产物字节或哈希；
  • 业务事件序列。

如果绝对路径、时间戳或对象枚举顺序进入产物，先判断它是否是语义必需信息。调试图可以显示相对路径，内部仍保留 canonical identity。

3

保存一次完整操作轨迹

从入口开始，记录 asset 发现顺序、每条 resolved edge、模块表记录和 runtime 进入/退出事件。选择一条最终日志，反向追到它来自哪个源文件、哪个 module id 和哪条父 mapping。

交付：一份可读 trace 和一次反向追踪说明。
