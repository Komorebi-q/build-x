P03 · Serialization

把模块图变成保留边界的程序文本

bundle 不是把文件首尾相接。你要把每个模块的代码隔离在包装函数里，把局部依赖映射保存进模块表，并让生成结果可解析、可检查、可复现。

45–65 分钟核心：module table产出：序列化契约与语法测试

先理解：bundle 同时包含代码和数据

模块表中的部分性质用途
模块 id数据键runtime 定位模块记录
包装函数可执行代码建立模块局部作用域并接收 runtime 能力
specifier → child id每模块局部数据让转换后的 require("./x.js") 找到正确节点
entry id启动数据告诉 runtime 从哪个节点开始执行
moduleTable 概念形状：
  moduleId → [moduleWrapper, localMapping]

moduleWrapper 接口：
  (localRequire, module, exports) → 执行转换后的模块代码

这只是接口形状，不规定你必须使用数组、对象或 Map。关键是序列化前后能恢复同一份关系。

为什么必须保留模块作用域

假设两个文件都在顶层声明 const state。简单拼接会产生重复声明，或者让一个模块意外读到另一个模块的变量。函数包装建立词法边界，并让 runtime 按模块注入 require/module/exports。

1

做一个“直接拼接必败”实验

准备两个无 import 的模块，它们声明相同顶层名字并产生不同日志。先预测字符串拼接的解析/执行结果，再比较函数包装后的结果。不要把此实验的修复与整个 runtime 一次写完。

交付：失败现象、原因和“函数边界修复了什么 / 没修复什么”说明。

代码生成边界：不要把所有东西都当字符串

  • mapping 是数据，应使用可靠的数据序列化方式；不要手工给路径加引号。
  • 转换后的模块代码需要作为函数体生成；要警惕注释、反引号、Unicode、换行和 sourceURL 等边界。
  • 输出应通过 JavaScript parser 的“整份程序可解析”测试，而不是只肉眼看起来像代码。
  • 同一图输入应产生字节稳定的输出；不要依赖未声明的文件系统枚举顺序。
安全问题与课程边界

打包器本来就在处理代码，最终产物会执行源码。这里的目标不是把不可信代码变安全，而是避免生成器因路径、映射或模板边界破坏产物结构。不要在构建阶段用 eval 执行待打包模块来“发现”依赖。

亲自完成：先生成模块表，再接启动壳

序列化图(graph):
  以稳定顺序遍历每个资产
  为每个资产生成：id、包装后的 code、序列化 mapping
  把所有模块记录组合成 module table
  把 module table 与 entry id 嵌入尚未填充细节的 runtime shell
  返回整份程序文本
2

为 serializer 写结构测试

  1. 单模块输出能被 parser 当成一份完整 script 解析。
  2. 两个模块相同顶层变量名不会处于同一词法作用域。
  3. 带引号、反斜线或非 ASCII 字符的 specifier/mapping 仍保持数据原值。
  4. 菱形图中两条父边的 mapping 都保留，并指向同一 shared id。
  5. 同一规范化图连续生成两次，输出完全一致。

交付：五组序列化测试、一个产物结构标注图和输出哈希对比。

产物阅读练习

选择一个三模块产物，给文本分区标注：

  1. runtime shell 的开始与结束；
  2. 每个 wrapper 的作用域边界；
  3. 每个 mapping 的所属父模块；
  4. entry id 从哪里进入 runtime；
  5. 业务源代码经 transform 后位于何处。

如果你无法从产物中指出这些边界，说明数据结构可能只存在于实现者脑中，调试时会非常困难。

提示 1：输出稳定性

先让 graph 提供明确的模块顺序或按稳定字段排序；不要在 serializer 中偷偷重新发现依赖。

提示 2：mapping 的语境

相同 raw specifier 在不同父模块中可能指向不同 id，所以 mapping 不能是一张脱离父模块的全局表。

提示 3：测试生成代码

“能解析”与“能正确执行”是两道关。本课先用 parser 锁定语法；下一课用受控 runtime 日志验证执行。
