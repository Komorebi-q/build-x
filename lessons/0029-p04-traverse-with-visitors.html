P04 · Traversal

先证明访问顺序，再让转换依赖它

遍历器不是“递归一下”就结束。你要明确每种节点的 child keys、parent 关系、enter/exit 顺序和未知节点策略，并用事件轨迹把契约锁住。

45–75 分钟核心：DFS + visitor产出：访问轨迹、child-key 表、失败策略

本节目标

按 schema 找孩子

Program 看 body，CallExpression 看 params，literal 没有 child。

区分 enter / exit

enter 在孩子前，exit 在所有孩子后，顺序可预测。

传递 parent

root 的 parent 为空，其余节点获得直接父节点。

未知节点安全失败

不静默跳过未来节点，错误保留节点类型与位置。

先手演一棵树

Program
└─ Call(add)
   ├─ Number(2)
   └─ Call(subtract)
      ├─ Number(4)
      └─ Number(2)
1

闭卷写 enter/exit 轨迹

为每个事件记录序号、动作、node.type、可读标签和 parent.type。然后用一个“只记录事件、不做转换”的 visitor 跑同一棵树，比较差异。

交付：预测轨迹与实际轨迹；任何差异都要解释。

遍历器的三个接口面

接口问题测试证据
child schema每种 node type 的孩子在哪些字段？每个 child 恰好访问一次且保持数组顺序
visitor dispatch缺少某类 visitor 是否允许？允许缺 handler，但仍遍历该节点的孩子
tree validity未知 node type 怎么办？结构化失败，不静默丢失整个子树

visitor 可以不关心某种已知节点；traverser 却必须知道怎样穿过每种已知节点。这两个“未知”不要混为一谈。

任务拆解

2

测试最小遍历器

  1. 空 Program：只有 root 的 enter/exit。
  2. 单 literal：parent 指向 Program。
  3. 嵌套 call：深度优先且 params 保持源码顺序。
  4. 只定义 NumberLiteral visitor：仍能穿过 Program 与 CallExpression。
  5. 注入未知 node：得到 UNKNOWN_NODE_TYPE 和节点 loc。
  6. visitor.enter 主动抛错：明确原样传播还是包装，并测试该契约。

检查点：事件测试比较结构化数组，不靠 console.log 人眼判断。

3

画 traversal stack

选择最深的嵌套输入，逐步画出调用栈；标出何时能执行 exit。回答：若在 enter 时创建目标父节点，为什么子节点随后能写入它的 arguments？

交付：调用栈图和一句不变量说明。

逐级提示

提示 1：遍历数组时 parent 是谁？

数组只是存储容器，不是 AST node；每个 child 的 parent 应是拥有该 child 数组的节点。

提示 2：没有 visitor 方法时怎么办？

跳过回调，但不要跳过 child traversal。节点 schema 和用户关心的 visitor 是两层决定。

提示 3：如何减少 switch 扩展成本？

可以先使用清晰 switch；提高阶段再比较集中 child-key map。核心是未知类型不被静默吞掉，而不是追求抽象。

自查问题

  1. pre-order、post-order 分别对应 enter 还是 exit？
  2. 为什么 literal 即使没有孩子，也仍应触发 enter/exit？
  3. visitor 缺少 CallExpression handler 与 AST 出现未知 FooExpression 有何不同？
  4. 若 visitor 在遍历期间修改正在迭代的 params，顺序契约会发生什么？核心阶段允许吗？
  5. 节点 location 如何帮助定位 transformer/traverser 的内部不变量错误？
