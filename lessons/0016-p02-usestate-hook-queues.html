P02 · Hooks & Update Queues

Hook 没有名字，位置就是身份

为函数组件 Fiber 保存 hooks 数组；每次 render 从索引零开始，按固定调用顺序读取旧 hook、消费更新队列并生成新 hook。

90–120 分钟难度：高产出：多个独立 state 与更新队列测试

先回答：第二次 render 如何找到“同一个 state”

old fiber.hooks[0]
→
第 1 次 useState
→
new hooks[0]
old fiber.hooks[1]
→

→
new hooks[1]

这个简化模型没有变量名映射。它只依赖组件在每次 render 中以相同顺序调用 hooks，因此条件分支中的 hook 会让后续位置错位。

1

手工推演两个 state 的三次 render

组件依次声明 count 与 label。第一次初始化，第二次只更新 count，第三次只更新 label。每轮画 old hooks、pending actions、new hooks。

交付：三轮 hook 槽位表，证明两个 state 独立。

一个最小 hook 记录需要什么

state

本次 render 计算完成后的状态快照。

queue

尚待下一次 render 应用的更新动作。

hook index

当前组件 render 中正在读取的位置。

wip fiber

当前正在执行的函数组件 Fiber。

每次执行函数组件前重置 hooks 数组与索引；每次调用 useState 都消费当前位置的旧 hook，按顺序应用其 queue，再把新 hook 放入候选 Fiber。

把 setState 理解成“排队动作 + 安排 root 更新”

setState(action) 的概念职责：
  1. 把 action 放进所属 hook 的 queue
  2. 以 current root 创建新的 work-in-progress root
  3. 重置 next unit 与 deletion 集合
  4. 等待工作循环重新计算整棵候选树

不要在 setter 内直接改 DOM，也不要只重算当前组件节点。本课程的简化策略从 root 重新开始，reconciliation 决定哪些 DOM 真正变化。

2

先支持函数式 action

让 action 以旧 state 计算新 state。连续排入两个 increment 后，下一次 render 应按队列顺序折叠，而不是两次都读取同一个旧快照。

交付：空队列、单 action、连续 actions、两个独立 hooks 四组测试。

用故障实验理解 Hooks 规则

在实验分支中，让第一个 useState 只在条件为真时调用。切换条件后记录第二个 state 从哪个旧槽位读取。不要修复它；先解释为什么顺序身份被破坏。

课程边界

你的实现不必构建静态 lint 规则，但文档和演示必须明确：hooks 只在函数组件顶层、以稳定顺序调用。

3

实现双计数器验收页面

一个组件内放两个独立 state，各有自己的更新按钮；再加一个同时更新两者的按钮。保存 DOM 引用并记录每次组件执行、hook state 与 DOM 提交。

交付：双 state 演示、操作序列和独立性断言。

逐级提示

提示 1：第二次 render 又回到初始值

确认新 Fiber 能通过 alternate 找到旧 Fiber 的 hooks，而不是每次只使用 initial 参数。

提示 2：两个 state 相互覆盖

记录每次 hook 调用前后的 hookIndex；检查索引是在何时递增、组件开始时是否归零。

提示 3：连续两次更新只增加一次

检查队列中保存的是已经计算好的值，还是稍后基于前一结果执行的 action；并确认 action 按注册顺序折叠。

提示 4：更新后又重复消费旧 action

候选 hook 应拥有本轮计算后的 state 与新的待处理队列；已消费动作不能在下一轮再次出现。
