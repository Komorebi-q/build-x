P04 · Code Generation

让每种目标节点只负责自己的打印规则

你将从目标 AST 递归生成稳定文本，并把逗号、括号、分号、换行与字符串转义变成明确契约，而不是散落在转换阶段的字符串拼接。

45–75 分钟核心：递归 printer产出：节点打印表、golden tests、输出语法验证

本节目标

按 node.type 分派

每种节点拥有局部、可组合的打印规则。

稳定格式

相同目标 AST 多次生成完全相同的代码。

正确编码字面量

字符串输出考虑引号和转义，不把原始 value 直接包起来。

验证目标语法

不仅比较文本，还让 JavaScript parser 对产物做语法检查。

先写节点打印表

目标节点输出规则组合边界
Program逐个打印 body语句之间用固定换行
ExpressionStatement打印 expression 后加分号分号只由 statement 负责
CallExpressioncallee + 括号内 arguments参数由逗号空格连接
Identifier输出 name只接受已验证的目标字段
NumberLiteral输出规范化 value数值范围由语言契约决定
StringLiteral输出可靠序列化后的字符串必须处理引号、反斜杠和控制字符

任务拆解

1

从叶子到组合节点测试

  1. Identifier、NumberLiteral、StringLiteral 单独测试。
  2. 零参数、一个参数、多个参数和嵌套 CallExpression。
  3. ExpressionStatement 的唯一分号责任。
  4. 多个顶层 statement 的换行策略。
  5. 未知 node type 返回带 phase、code、loc 的内部诊断。

检查点：每个小节点失败能定位到一个打印规则。

2

补容易被 happy path 隐藏的字符串

至少测试包含双引号、反斜杠、换行或 tab 的 value。先写下你允许的源字符串语法；即使 tokenizer 暂不支持转义，也要确保 generator 对目标 AST 输入的契约清晰。

检查点：生成结果能被 JavaScript parser 接受，且求值时字符串值不变（若做运行测试，请隔离并限制输入）。

3

建立双层 oracle

  1. 文本 oracle：少量小 AST 使用精确字符串断言。
  2. 语法 oracle：所有合法目标 AST 的输出都能被可靠 JavaScript parser 解析。
  3. 确定性 oracle：同一 AST 连续生成两次完全一致，AST 本身未被修改。

交付：节点打印表、golden cases 和语法验证摘要。

格式化不是语义本身

Babel Generator 官方说明：AST 通常不保存所有原始空白与换行，重新生成的格式不保证复刻输入。你的最小 generator 也应明确：

  • 保证目标代码语法与含义；
  • 保证课程定义的确定格式；
  • 不保证保留源语言空白、括号风格或注释；
  • 没有 source map 时，输出位置不能自动反查源位置。

逐级提示

提示 1：逗号由谁打印？

让 CallExpression 负责连接已打印 arguments；参数节点不知道自己是不是最后一个，也不应自行加逗号。

提示 2：字符串如何避免手写不完整转义？

考虑使用语言已有的可靠字符串序列化原语，并用目标 parser 验证；先明确它产生的引号风格是否属于你的格式契约。

提示 3：为什么不能执行任意输出验证？

语法验证只需 parse。若额外求值，只使用课程自有固定 AST 与受控函数环境，避免把未知生成文本当作可信代码执行。

自查问题

  1. 为什么分号应由 statement 而不是 call 打印？
  2. 为什么 argument 节点不应知道逗号位置？
  3. 精确字符串测试与 parser 语法测试分别能发现什么？
  4. 若未来支持运算符，为什么 precedence 会迫使 generator 了解更多父子上下文？
  5. location 与 source map 有什么关系，又为什么不等价？
