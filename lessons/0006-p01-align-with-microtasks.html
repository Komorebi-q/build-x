P01 · Scheduling

让 reaction 永远越过当前调用栈

Promises/A+ 只要求“稍后”；现代原生 Promise 使用 reaction jobs。你将用顺序实验选择 scheduler，并证明同步与异步结算拥有一致的观察行为。

30–45 分钟 难度：中等 产出：调度顺序测试

先分清两个合格标准

Promises/A+ 合格

handler 不在调用 then 的当前执行栈内运行。规范注释允许宏任务或微任务方案。

贴近原生行为

ECMAScript 创建 PromiseReactionJob，并让 host 排队；在常见 JS 环境中表现为微任务时序。

因此，原始教程使用 timer 可以满足 A+ 的“新栈”要求，却不能复制原生 Promise 相对 timer 的顺序。本项目的提高目标是用 queueMicrotask 对齐常见原生行为。

顺序实验：同一轮里谁先执行

先写预测，再运行：

console.log("A: sync start");

setTimeout(() => console.log("D: timer task"), 0);
queueMicrotask(() => console.log("B: manual microtask"));
Promise.resolve().then(() => console.log("C: promise reaction"));

console.log("E: sync end");
1

画出三段队列时间线

  1. 标出同步代码的起止。
  2. 按入队顺序写出两个微任务。
  3. 最后放置 timer task。
  4. 交换 queueMicrotask 与 Promise.resolve().then 两行，再预测一次。

交付：两条输出顺序和一张“当前栈 → 微任务排空 → 下一个 task”的时间线。

核对结果

首次顺序应为 A → E → B → C → D。两个微任务按入队顺序执行；交换入队语句后 B/C 也应交换。课程不依赖 Node 特有的 process.nextTick。

为什么 settled 后注册也必须异步

如果缓存命中时同步调用 handler、网络返回时异步调用 handler，调用者就必须猜测回调是否会“突然重入”。统一越过当前栈可以避免这种时间不一致，也常被称为避免 Zalgo。

场景错误实现正确不变量
先 then，后 settle排队后异步执行异步执行
先 settle，后 then看到结果后立即调用仍通过 scheduler 异步执行
handler 中再 then可能递归重入新 reaction 继续排队

把顺序写成测试，而不是延时猜测

2

建立五个调度断言

  1. handler 在 then 返回前不执行。
  2. 同步 resolve 的 handler 也要等当前栈结束。
  3. 已 fulfilled 后新增 handler 仍异步。
  4. 同一 Promise 的多个 reactions 保持 FIFO。
  5. reaction 在后续 timer task 之前执行。

优先用一个 trace 数组记录事件，再在最终 timer 或测试框架的异步能力中一次断言完整顺序；不要给每一步随意加几十毫秒等待。

交付：五个稳定通过的顺序测试，连续运行多次无偶发失败。

替换生产 scheduler，保留测试边界

第三课已经把 scheduler 抽成依赖。现在让生产版本使用微任务机制，同时保留可控测试 scheduler：

reaction runner 只负责：选择 handler、传播结果
scheduler 只负责：决定 job 何时进入执行

生产：enqueue(job) → 微任务
测试：enqueue(job) → 可控队列
3

完成调度器替换与差分实验

  1. 保持 reaction runner 不变，只替换生产 scheduler。
  2. 使用相同 trace 脚本分别运行原生 Promise 与你的实现。
  3. 比较同步日志、reaction、timer 的相对顺序。
  4. 记录仍存在的行为差异，不要为了“看起来一样”修改不相关逻辑。

交付：一份差分顺序表，至少包含 pending 前注册与 settled 后注册两种场景。

微任务不是免费的

微任务饥饿

事件循环会持续排空微任务；若每个微任务无条件再创建一个微任务，timer、输入事件和渲染可能长时间得不到机会。你的 Promise 实现应调度有限 reactions，不要建立无界自循环。

这也是为什么调度策略属于明确边界：以后做 React 调度或服务器 backpressure 时，你会再次遇到“低延迟”与“公平让出”的取舍。

闭卷自查

  1. Promises/A+ 为什么可以接受 timer，而本项目仍选择微任务？
  2. resolve 是同步还是异步？handler 又是什么时机？
  3. 为何已 settled 的 Promise 也不能 inline 调 handler？
  4. 如果 reaction job 抛错，应该如何影响 child，而不是泄漏到 scheduler？
核对关键词

A+ 最低互操作要求与原生时序不同；resolve 同步锁定、handler 排队；统一时间语义避免重入；reaction runner 捕获 handler 异常并 reject child。
