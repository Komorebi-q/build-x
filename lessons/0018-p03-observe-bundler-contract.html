先预测，再运行参考项目

  1. 预测三个模块被发现、转换和执行的顺序。
  2. 预测 bundle 内至少需要保存哪些数据，才能让入口找到下一层依赖。
  3. 先读 package.json 并记录旧依赖。若要运行，把仓库复制到工作区外的一次性目录，再按 README 安装；把打包器标准输出保存为临时 bundle，不在固定快照中生成依赖或 lockfile。若旧依赖与当前 Node 不兼容，保留错误证据，不要升级快照。
  4. 先在生成文本中找出模块包装函数、specifier → id 映射和入口启动位置；再把临时 bundle 作为独立程序执行，分开记录 build output 与最终业务日志。

交付：“预测 / 观察 / 修正解释”三列表；每个结论附一段输出证据。

前置诊断：闭卷回答

  1. 为什么用正则搜索 import 不能可靠地代替 JavaScript parser？至少给出两个反例类别。
  2. ./name.js 是完整文件身份，还是相对某个 importer 才有意义的 specifier？
  3. 树和有向图有什么不同？“两个模块都依赖同一文件”会形成什么形状？
  4. 为什么把每个模块包进函数可以避免顶层变量互相污染？
  5. “图中只有一个共享节点”能否直接证明“运行时只执行共享模块一次”？为什么？
  6. ESM 的 import binding 与从普通对象解构一个值有什么潜在语义差异？

确定 P03 的完成边界

核心阶段必须完成核心阶段明确不承诺
单一 JavaScript 入口、静态相对 ESM import动态 import、package exports、alias、网络 URL
AST 提取依赖并转换已声明的 ESM 语法自己编写 JavaScript parser 或完整转译器
按规范化文件路径建立可打印的有向图tree shaking、chunk splitting、生产优化
模块表、局部加载函数、入口启动完整复刻原生 ESM 链接与 live binding
链式与菱形依赖、错误路径、确定性测试核心验收前实现插件系统、source map 或 watch

模块缓存和循环依赖先作为“可观测的教学缺口”保留到第 7 课。不要在还没稳定基本图和 runtime 前同时扩展范围。
