P04 · Syntactic Analysis

让递归结构来自文法，而不是括号计数猜测

你将把扁平 token 流解析为源语言 AST。每次 parseExpression 消费且只消费一个完整表达式，嵌套调用自然通过递归形成。

60–90 分钟核心：递归下降产出：源 AST、消费不变量、语法错误矩阵

本节目标

维护 token cursor

peek 只看，consume 明确前进，EOF 是可测试状态。

解析一个表达式

literal 与 call 都遵守“恰好消费一个完整表达式”。

组合节点 span

父节点从起始 token 到结束 token 形成完整半开区间。

区分语法错误

缺名字、意外右括号、缺结束括号和未知 token 分别诊断。

先理解消费不变量

parseProgram:
  当未到 EOF：反复调用 parseExpression

parseExpression:
  若当前是 number/string：消费一个 token，返回 literal
  若当前是左括号：调用 parseCall
  否则：报告当前位置的语法错误

parseCall:
  消费左括号与紧随其后的 name
  反复解析参数，直到右括号
  消费右括号，返回 call

这是控制流草图，不是最终实现。你要先用测试证明每条路径消费多少 token，以及失败时错误指向哪个 token 或 EOF。

任务拆解

1

先锁定 AST schema

为 Program、NumberLiteral、StringLiteral、源语言 CallExpression 写字段表。每种节点都包含 type 与 loc；call 使用 name 和 params。

检查点：AST 可以表达两个顶层表达式与至少三层嵌套调用。

2

按复杂度逐步变绿

  1. 空程序与单个 literal。
  2. 无参数调用与多个参数调用。
  3. 嵌套调用。
  4. 多个顶层表达式。
  5. 每个节点的 source span。

检查点：不要从最终大 AST 快照起步；每一步只增加一种结构。

3

设计语法错误矩阵

交付：节点 schema、阶段测试和至少四个语法错误对象。

父节点位置如何合成

  • literal：直接继承 token 的 start/end。
  • call：start 来自左括号，end 来自右括号消费后的 end。
  • program：有 body 时覆盖首尾表达式；空程序使用文件起点的零宽 span，或清晰声明 loc=null。
  • 不要根据 value 长度倒推位置；字符串 value 可能不包含引号，换行与未来转义也会破坏推算。

逐级提示

提示 1：嵌套调用怎样停在正确右括号？

内层 parseCall 会消费自己的右括号并返回；外层游标因此落在外层的下一个参数或右括号上。每一层只对自己的边界负责。

提示 2：为什么 EOF 不能直接读取 token.type？

EOF 不是普通 token 时，peek 可能返回空值。所有需要 token 的分支都要先决定 EOF 是否是合法终止或结构化错误。

提示 3：如何避免“接受 (add)”却没验证 name？

把 expect(type, value?) 看作一种带诊断的消费操作；它返回已验证 token，而不是先随意前进再取 value。

自查问题

  1. parseExpression 成功后，游标必须满足什么不变量？
  2. 为什么 Program.body 是数组，而调用参数也是数组，但两者终止条件不同？
  3. parser 是否应该接受 tokenizer 根本不会产生的 token？如果收到，应如何失败？
  4. 未闭合调用的错误主位置放 EOF 时，为什么还值得保留起始左括号位置？
  5. AST 快照测试之外，你如何单独证明 span 正确？
