实验：一个表达式经历了什么

输入：      (add 2 (subtract 4 2))
token：    paren/name/number/...
源 AST：   CallExpression(name, params)
目标 AST： CallExpression(callee, arguments)
输出：      add(2, subtract(4, 2));

先预测，再运行上游测试

  1. 只看上面的输入和输出，画出你预测的两棵 AST；标出为什么需要两棵而不是一棵。
  2. 阅读 上游测试，把预期 token、源 AST、目标 AST 与你的预测逐项比较。
  3. 运行 node sources/the-super-tiny-compiler/test.js；然后只改一次临时副本中的输入，记录第一处失败发生在哪个阶段。
  4. 阅读 带讲解的上游源码，只写阶段输入、输出与限制，不抄函数体。

阶段只负责不要偷做
Tokenize字符分类、合并词素、记录位置不决定调用嵌套关系
Parse按文法组织源 AST不打印目标代码
Transform把源 AST 语义映射到目标 AST不靠字符串拼接隐藏结构
Generate按目标节点递归打印代码不重新猜源语法
Diagnostics跨阶段保存 source、span、code、message不把所有错误压成一个字符串

先写语法，再写循环

Program     := Expression*
Expression  := Number | String | Call
Call        := "(" Name Expression* ")"

核心支持：十进制非负整数、双引号字符串、英文字母函数名、任意空白
核心不支持：运算符、负数、小数、转义、注释、变量、定义、JavaScript 源码

这份文法是你的公开契约。若决定扩展，先改文法与测试矩阵，再改实现；不要让某个正则表达式偶然定义语言。

前置诊断：闭卷回答

  1. token 与 AST node 的差异是什么？括号为什么可以成为 token，却不必成为 AST node？
  2. 为什么 parser 比 tokenizer 更适合决定嵌套调用的父子关系？
  3. 源 AST 与目标 AST 都叫 CallExpression 时，哪些字段能证明它们仍是不同 schema？
  4. 深度优先遍历中 enter 与 exit 的可观察顺序是什么？
  5. 位置的 end 应指向最后一个字符，还是片段后的第一个位置？两种选择对切片有何影响？
  6. 为什么只断言最终字符串不能证明四个阶段分别正确？
第 3 题提示 1

比较源节点的 name / params 与目标节点的 callee / arguments，再看顶层 statement 包装。

第 5 题提示 1

第 6 题提示 1
