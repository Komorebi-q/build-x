P01 · TDD 状态机

先写不变量，再写状态

这一课只完成最小构造与一次性迁移。暂时不做完整 then，也不吸收 thenable；让每个测试只推动一个设计决定。

35–50 分钟 难度：基础 产出：状态机测试组

本课边界

现在实现

executor 立即调用、初始状态、第一次 resolve / reject 获胜、executor 异常转 rejection。

刻意推迟

handler 队列、链式 then、thenable 吸收、微任务细节、静态组合方法。

阶段性脚手架不是最终语义

本课只用普通值测试 resolve。原生构造器的 resolve 会吸收 thenable；第五课会把“临时 fulfill”重构为完整 resolution procedure。请在代码中留下明确 TODO，避免误把阶段实现当完成品。

从行为表生成测试

场景刺激必须观察到防止的错误
构造传入 executor立即且仅调用一次；收到两个函数把 executor 错误地排到以后
初始executor 不结算保持 pending默认 fulfilled 为 undefined
成功resolve 普通值fulfilled，保存同一值丢失 value 或多次变化
失败reject reasonrejected，保存同一 reason强制 reason 必须是 Error
竞争resolve 后 reject第一次调用获胜两个 closure 各自维护独立开关
异常executor 直接 throw以该异常 rejected异常逃出构造器
迟到异常resolve 后 throw保持首次结果catch 覆盖已锁定结果
1

把七行行为表改写成测试名

使用“给定—当—那么”思路，但测试名应描述外部行为，不描述你的字段名。例如，避免写“called 标志变为 true”。

交付：七个测试名；每个名字都能在不看实现时读懂。

决定如何观察状态

在 then 尚未完成时，测试状态机有两种合理方案：

测试专用快照

通过只读调试接口读取 state / result。反馈直接，但必须防止它变成公共可写 API。

暂时暴露内部状态

更接近原始教程，启动快；后续要主动收回，否则用户可以破坏不变量。

2

写一条设计决定

选择一种观察策略，写下“为什么适合学习阶段”和“何时删除或收紧”。不要因为测试方便就永久扩大公共 API。

交付：三句话的测试可观察性决定。

一次只让一个测试变绿

按下面的设计骨架推进。它是伪代码，刻意不提供 JavaScript 最终实现：

构造(executor)
  初始化：状态为 pending，结果为空
  创建一个“是否已决定”的共享闩锁

  resolveOnce(value)
    如果闩锁已关闭：忽略
    否则关闭闩锁，暂时以普通值完成

  rejectOnce(reason)
    如果闩锁已关闭：忽略
    否则关闭闩锁，以 reason 拒绝

  尝试立即调用 executor(resolveOnce, rejectOnce)
  如果抛错：交给 rejectOnce

关键不是字段怎么命名，而是 resolve 与 reject 必须共享同一个竞争闩锁，executor 的异常也必须走相同的一次性入口。

3

执行 Red → Green → Refactor

  1. 选择行为表第一行，先看到测试因正确原因失败。
  2. 只写让这一行变绿的最少代码。
  3. 每次新增测试后运行整个小组，防止旧不变量回归。
  4. 七行全部变绿后，再消除重复；不要提前抽象。

交付：七个通过的测试、至少一个红灯截图或日志，以及一次小重构说明。

卡住时按层取提示

提示 1：第一次调用为何没有被锁住？

检查 resolve 与 reject 是否引用同一个词法作用域中的布尔状态。若各自有一个标志，它们无法互斥。

提示 2：executor 抛错为何逃出去了？

异常边界应该包住“调用 executor”这个动作，而不是包住 executor 的创建。捕获后不要直接改状态，要复用一次性 reject 入口。

提示 3：resolve 后 throw 为何变成 rejected？

这说明 catch 绕过了共享闩锁。让捕获到的异常也调用 rejectOnce，已关闭时自然被忽略。

闭卷自查

  1. 为什么只检查 state !== pending 也能实现一次性迁移？它与独立闩锁在 thenable 吸收阶段可能有什么差别？
  2. 为什么 rejection reason 不应该强制转成 Error？
  3. executor 先 resolve 再 throw 时，哪个规则决定最终结果？
  4. 本课的 resolve 为什么仍是“暂时不完整”的？
核对思路

前三题分别考察状态不变量、规范允许任意 reason、第一次决定获胜。第四题的关键是：完整 resolve 还需递归处理 Promise / thenable，并区分“锁定”与“已 fulfilled”。
