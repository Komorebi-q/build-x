P01 · Conformance

让外部测试套件挑战你的实现

自己的测试容易只覆盖自己想得到的情况。官方 Promises/A+ 套件会用大量对抗性 thenable 验证 then；你的任务是按规范条款定位失败，而不是盲目改到全绿。

40–60 分钟 难度：困难 产出：兼容性报告

测试套件只需要一个很小的桥

promises-aplus-tests 不需要理解你的类名或目录结构。它通过 adapter 取得三个能力：

导出职责是否必需
deferred()返回 { promise, resolve, reject }，初始 promise 为 pending核心入口
resolved(value)创建已以 value fulfilled 的 promise可选，但有助于覆盖
rejected(reason)创建已以 reason rejected 的 promise可选，但有助于覆盖
adapter 不是第二套实现

它只把测试套件的三个动作翻译到你的公共 API。若 adapter 里出现状态机、队列或解析逻辑，说明你正在用桥接代码掩盖真实缺陷。

先写 adapter 契约草图

deferred()
  在构造自定义 Promise 时捕获 resolve 与 reject
  返回：promise + 两个已捕获函数

resolved(value)
  使用公开构造方式创建已完成实例

rejected(reason)
  使用公开构造方式创建已拒绝实例
1

实现最薄 adapter

  1. 先只实现 deferred，写一个烟雾测试确认三项身份正确。
  2. 确认 adapter 的 resolve / reject 自身不会把重复结算错误抛到测试套件外。
  3. 再按你的公共 API 决定是否提供两个可选导出。

交付：adapter 文件与一个不含 Promise 逻辑的说明。

运行全套，再缩小失败范围

在你的学习实现目录中安装并运行测试工具：

npm install --save-dev promises-aplus-tests
npx promises-aplus-tests path/to/your-adapter

该 CLI 会把后续选项传给 Mocha，因此可以按条款聚焦：

npx promises-aplus-tests path/to/your-adapter --grep "2.3.3"

保存第一次完整结果

第一次失败列表是学习证据，不要清屏。按条款前缀归类，而不是按报错文本逐个打补丁。

交付：首次通过 / 失败摘要，以及失败最多的前三个规范区域。

用条款地图定位不变量

一次修复一个根因簇

  1. 选择失败最多的一个条款前缀。
  2. 用 --grep 只运行该簇。
  3. 从失败中提取一个最小复现，先加入自己的回归测试。
  4. 修复对应不变量，运行该簇、自己的测试、最后再跑全套。
  5. 记录“根因 → 影响条款 → 修复证据”。

交付：至少一条从官方失败转成自有回归测试的记录。

全绿不等于原生 Promise 完成

Promises/A+ 明确聚焦 then 互操作，不规定所有原生构造器与静态方法。即使套件全绿，你自己的测试仍要负责：

  • executor 是否立即且只调用一次；executor 抛错如何处理。
  • 你是否选择了微任务级时序，而不只是“某种异步”。
  • catch、后续扩展方法与调试接口的行为。
  • 项目自己的模块格式、公共 API 与回归边界。
不要改测试来换全绿

官方套件是外部裁判。若你认为条款或测试有问题，先写最小复现、引用规范并单独记录；不要在依赖目录里直接改预期。
