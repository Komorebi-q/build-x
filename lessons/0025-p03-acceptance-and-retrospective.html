1

整理可重复运行的证据

  1. 记录 Node、包管理器与关键 parser/transform 版本。
  2. 给出从干净环境安装、运行、测试和生成 bundle 的精确命令。
  3. 保存测试摘要，不只提供绿色终端截图。
  4. 保存一次链式或菱形输入的 build trace、图和 runtime trace。
  5. 记录一个失败假设如何被最小测试推翻。

交付：命令、环境、测试矩阵、轨迹与排错记录。

关卡三：十分钟闭卷讲解

  1. 从一个入口文件走到 asset，并解释 AST visitor 读取了什么。
  2. 解释 raw specifier、canonical filename 与 module id 的区别。
  3. 画菱形图，说明节点去重、两条边和执行缓存是三个问题。
  4. 解释 wrapper、module table 与 parent-local mapping。
  5. 手演三层 localRequire 调用与 exports 返回。
  6. 说明你的实现与原生 ESM、Node resolution、生产 bundler 的至少五个差距。

关卡五：模型边界声明

至少明确以下内容是否支持、如何失败，以及它与真实语义的差距：

  • 只支持哪些静态 import/export 形式；
  • specifier resolution 的精确规则；
  • 是否按 canonical filename 去重 asset；
  • 是否缓存模块实例，菱形副作用执行几次；
  • 循环依赖是支持、检测报错还是尚有近似限制；
  • Babel ESM → CommonJS 转换不等于原生 ESM 链接与 live binding；
  • 不包含 tree shaking、code splitting、source map、插件和增量构建中的哪些部分。

通过核心验收不表示兼容 Webpack、Rollup、Vite、Node 或浏览器原生模块系统。

复盘问题

  1. 哪个 bug 最能说明 specifier 不是全局文件身份？

  3. 你在哪个阶段最容易混入另一个阶段的职责？为什么？
  4. 哪个错误消息最初丢失了 importer 或源码位置？你如何补回？
  5. 如果开始 P04 编译器，你会复用哪三个 AST/transform 测试习惯？
  6. 两周后闭卷重画，你最可能忘记 module table 的哪条关系？
